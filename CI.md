# Лабораторная 2 — как работает CI/CD

## Локальный запуск

Нужны Docker Desktop с Linux-контейнерами, Git for Windows и act.
Установка act из PowerShell:

```powershell
winget install nektos.act
```

После установки откройте **Git Bash** в корне проекта:

```sh
sh ci/run-local.sh
```

Скрипт сам создаёт два разных пароля CI-БД в окружении процесса.
Настраивать рабочий `.env` или запускать БД первой лабораторной не требуется.
При первом запуске нужен интернет для загрузки образов, actions и зависимостей.
Одновременно запускайте только один локальный конвейер.

## Что делает run-local.sh

1. Собирает `ci/Dockerfile.runner`: Python для скриптов, Node для GitHub actions,
   Docker CLI для Deploy.
2. Скачивает официальные actions в `.cache/actions/`, если их ещё нет.
3. Создаёт CI-пароли, если они не заданы в окружении.
4. Вызывает act и передаёт ему workflow, образ раннера и имена секретов.

`.actrc` содержит настройки act. `.actignore` исключает из копирования `.env`,
виртуальное окружение, кэш и другие локальные данные. Серверы артефактов и кэша
слушают localhost:34567 и localhost:34568; контейнеры обращаются к ним через
`host.docker.internal`. Настройки этого запуска рассчитаны на Docker Desktop.

## Что выполняется внутри стадий

| Стадия | Что происходит                                                                           | Результат                                |
| ------ | ---------------------------------------------------------------------------------------- | ---------------------------------------- |
| Build  | `ci/build.sh` проверяет Python через compileall и упаковывает исходники                  | `application-build` с `source.tar.gz`    |
| Test   | Получает архив Build, ставит зависимости и запускает `ci/test.py` с отдельной PostgreSQL | `junit-report` с JUnit XML               |
| SAST   | Semgrep проверяет app, db, ci и main.py по `.semgrep.yml`                                | `sast-report` с JSON-отчётом             |
| Deploy | `ci/deploy.sh` собирает образ, запускает Compose и ждёт готовности                       | Docker-образ `.tar.gz` и адрес `/health` |

В Test выполняются **25 тестов** из `tests/`. Ненулевой код тестов останавливает
конвейер. В SAST флаг `--error` делает то же при срабатывании правил ERROR,
которые в наборе помечены HIGH/CRITICAL. Ошибка сканера тоже останавливает
конвейер. Это небольшой учебный набор правил, а не проверка всех уязвимостей.

**Кэш** хранит загруженные pip-пакеты для ускорения повторных запусков Test/SAST.
**Артефакты** сохраняют результат стадии или передают его дальше: исходники,
отчёт тестов, отчёт сканера, готовый образ. Локально они находятся в `.artifacts/`,
на GitHub — на странице запуска workflow. Загрузка однопоточная для совместимости с act.

## Как устроены Dockerfile и Deploy

В Dockerfile две стадии. `build` готовит зависимости и проверяет код;
`runtime` получает зависимости и файлы, нужные для запуска.
`USER 10001:10001` задаёт непривилегированного пользователя. Команда
`chmod -R go-w /opt/file-manager` запрещает группе и остальным пользователям
изменять код. Рабочая папка `/workspace` доступна пользователю приложения.

`compose.ci.yaml` описывает отдельный проект `file-manager-ci`:

1. `db` запускает PostgreSQL и ожидается до готовности.
2. `init-db` выполняет `python -m db.init_db`, затем завершается.
3. `app` запускается после успешного init-db. Пароль администратора ему не передаётся.

`deploy.sh` удаляет прежний демонстрационный стек, собирает образ и вызывает
`compose up --wait`. Docker HEALTHCHECK обращается к `/health`; обработчик
в `app/health.py` подключается к БД и проверяет её. Ошибка готовности прерывает Deploy.
Далее `docker image save` сохраняет образ, gzip сжимает его для артефакта.

## Как посмотреть результат и открыть приложение

После успешного локального Deploy выполните в Git Bash:

```sh
docker compose --env-file ci/runner.env -f compose.ci.yaml ps
docker compose --env-file ci/runner.env -f compose.ci.yaml port app 8080
```

Порт выбирается автоматически. Если показано `127.0.0.1:49152`, откройте
`http://127.0.0.1:49152/health`: ожидается `{"status":"ok"}`.

Открыть консоль приложения в контейнере:

```sh
docker compose --env-file ci/runner.env -f compose.ci.yaml exec app python /opt/file-manager/main.py
```

Выполните `register`, затем `login`. Эти пользователи и файлы относятся к
демонстрационной среде; файлы в `/workspace` исчезнут при удалении контейнера.

Удалить только CI-стек, его сеть и том БД:

```sh
docker compose --env-file ci/runner.env -f compose.ci.yaml down --volumes
```

Каждый следующий Deploy также начинает с удаления предыдущего CI-стека.
При успешном запуске через act стек остаётся для демонстрации; при ошибке или
на GitHub очищается автоматически. Рабочая БД первой лабораторной отдельная.
Образ и отчёты сохраняются. Из распакованного артефакта образ можно загрузить
командой `docker load -i file-manager-image.tar.gz`.

Тесты и их запуск описаны в [TESTING.md](TESTING.md).
