# Проверка зависимостей в GitHub Actions

Стандартные наборы сохранены в `ci/semgrep-rules/`. CI читает локальные снимки и не требует загрузки правил из Registry при каждом запуске. Источник снимков — `https://semgrep.dev/c/p/python` и `https://semgrep.dev/c/p/security-audit`, дата загрузки 2026-11-20. Обновление выполняется явно с повторной проверкой результатов.

SAST использует локальные снимки стандартных наборов Semgrep `p/python`, `p/security-audit` и локальный `.semgrep.yml`. Все уровни находок сохраняются в отчётах. Находки всех уровней информационные и не блокируют деплой. Шаги SAST используют continue-on-error: ошибки сканирования и формирования отчётов не проваливают джобу и не блокируют деплой.

## Пэйлоады и область проверки

`tests/test_security_payloads.py` адаптирует примеры PayloadsAllTheThings к функциям файлового менеджера. Все обращения направлены на временные файлы-маркеры. Для XML с DTD дополнительно проверяется отклонение до создания парсера.

| Раздел справочника | Проверки |
|---|---|
| Directory Traversal | Относительные выходы, смешанные разделители, абсолютные/дисковые/UNC-пути, NUL и кодированные варианты. URL-кодирование в CLI сохраняется буквально, принятый путь должен оставаться внутри заданной границы |
| XXE Injection | Локальная внешняя сущность, SYSTEM/PUBLIC, внешняя DTD, параметрическая сущность, ограниченное расширение сущностей, объявление UTF-16, отсутствие раскрытия XInclude |
| Zip Slip | Выходы из папки распаковки, абсолютные пути, архивные симлинки и специальные файлы. После отказа папка назначения отсутствует, внешний маркер сохранён |
| Command Injection | Метасимволы оболочки в именах проверяются как буквальные данные файловой операции |

Тест `test_sql_parameters_preserve_filename` в `tests/test_manager.py` отдельно проверяет SQL-подобное имя файла на настоящей CI-базе. Тесты жёстких ссылок, лимитов и очистки временных файлов в `test_file_safety.py` написаны по реализации приложения.

Веб-специфичные разделы (XSS в браузере, SSRF веб-эндпоинтов, загрузка PHP/JSP, JWT, OAuth, GraphQL) требуют соответствующих интерфейсов. У файлового CLI таких интерфейсов нет. Примеры эксплуатации конкретных чужих продуктов и разрушительные проверки не входят в набор. Эти тесты не подтверждают отсутствие гонок при конкурентной подмене файловой системы.

Дополнительные форматы артефактов: `sast-report` включает `semgrep.sarif` и `semgrep.pdf`, а `dependency-audit` — `dependency-audit.pdf` и SBOM `sbom.cdx.json` (CycloneDX JSON). Исходные JSON и Markdown также сохраняются. SARIF пока сохраняется как скачиваемый артефакт; загрузка в GitHub Code Scanning отдельно не настроена.

В запуске Actions откройте **Summary**. Артефакт **dependency-audit** содержит исходный JSON и читаемый Markdown. Для каждой находки показаны пакет, версия, идентификаторы (в том числе CVE при наличии), описание и известные версии с исправлением.

Отчёт отображает серьёзность, если она присутствует в данных сканера. В стандартном JSON pip-audit оценка CVSS недоступна. Её сверяют по записи CVE или бюллетеню поставщика. Открытые находки сохраняются в отчёте и не блокируют деплой. Неполное сканирование и ошибки сканера блокируют деплой.

Артефакт **sast-report** содержит JSON и Markdown Semgrep. Сводка на странице запуска показывает правило, файл, строку, серьёзность правила, его поле `impact` и рекомендацию. `ERROR` обозначает серьёзность находки и не блокирует CI; `CRITICAL` в поле `impact` задан локальным правилом и не является оценкой CVSS.

Для демонстрации защиты файлов показывайте тесты запрета записи за пределы назначения ZIP, ограничения размера распаковки и отклонения жёстких ссылок. Последний сначала проверяет, что обычный файл доступен для проверки пути, затем убеждается, что политика отклоняет ссылку на него.

## Как показать исправление

1. Сохраните ссылку на запуск со срабатыванием и зафиксируйте идентификатор и версию пакета.
2. Обновите зависимость до совместимой версии с исправлением и запустите тесты.
3. Откройте новый Summary и проверьте, что находка исчезла. В PR укажите, какая версия была заменена и приложите ссылки на оба запуска.

## Как показать исключение

Проверка читает `ci/dependency-exceptions.json`. Для демонстрации можно передать скрипту синтетический JSON pip-audit с пакетом `demo-package`, версией `1.0` и находкой `DEMO-ONLY`. С пустым списком исключений она отображается как **Open**, код выхода 1. С временным исключением ниже она остаётся в отчёте как **Exception**, код выхода 0, если других проблем нет. В рабочем списке исключений записей нет.

```json
[
  {
    "package": "demo-package",
    "version": "1.0",
    "id": "DEMO-ONLY",
    "reason": "Синтетическая находка для демонстрации, реальный пакет не используется",
    "expires": "2030-01-01"
  }
]
```

Для реальной находки в причине указывают проверяемые факты и ссылку на разбор в PR или issue. Исключение действует только для указанного пакета, версии и идентификатора до конца указанного дня по UTC. После истечения срока находка снова отображается как открытая; в информационном режиме она не блокирует деплой.
